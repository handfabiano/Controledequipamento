# Banco de Dados

Fonte da verdade: `server/database/schema.sql` (SQLite) e `schema.pg.sql` (Postgres).

## Tabelas
| Tabela | Campos-chave | Observações |
|---|---|---|
| `usuarios` | `email` único, `senha` (bcrypt), `tipo`, `ativo` | tipos: coordenador, responsavel_entrega, responsavel_recebimento, tecnico |
| `depositos` | `nome`, `endereco`, `responsavel_id→usuarios` | |
| `categorias_equipamentos` | `nome`, `tipo` (som/iluminacao/palco/outro) | |
| `equipamentos` | `codigo` único (`XXX0000`), `tombamento` único (`TOMB-AAAA-NNNNNN`), `categoria_id`, `deposito_id`, `status`, `condicao`, `qrcode_gerado` | status: disponivel, em_uso, manutencao, com_problema, transferencia · condição: excelente…quebrado |
| `problemas_equipamentos` | `equipamento_id`, `gravidade`, `resolvido`, `reportado_por`, `resolvido_por` | gravidade: baixa/media/alta/critica |
| `templates_eventos` | `nome`, `tamanho` (pequeno/medio/grande/extra_grande) | |
| `checklist_template` | `template_id`, `categoria_id`, `quantidade_minima`, `obrigatorio` | base do checklist |
| `eventos` | `nome`, `local`, `template_id`, `data_inicio`, `data_fim`, `status`, `criado_por` | status: planejamento, aprovado, em_andamento, concluido, cancelado |
| `responsaveis_evento` | `evento_id`, `usuario_id`, `area`, `tipo` | |
| `equipamentos_evento` | `evento_id`, `equipamento_id`, `responsavel_id`, `area`, `quantidade`, `status` | status: planejado, confirmado, em_transito, entregue, devolvido |

Índices: status/depósito/tombamento de equipamentos, status de transferências, status e datas de eventos, `(usuario_id, lida)` de notificações.

## Regras ao alterar o schema
1. Edite **ambos** os arquivos de schema com sintaxe equivalente (`AUTOINCREMENT` vs `GENERATED BY DEFAULT AS IDENTITY`, `DATETIME` vs `TIMESTAMPTZ`).
2. Apenas `CREATE TABLE/INDEX IF NOT EXISTS`. O `init.js` quebra o arquivo por `;` — não use `;` em comentários, strings ou blocos `DO $$`.
3. `CREATE TABLE IF NOT EXISTS` **não altera tabelas existentes**. Para nova coluna em bancos já criados é preciso migração idempotente (ver skill `migracao-banco`). Nunca presuma que produção será recriada.
4. Toda tabela precisa de coluna `id` (o `RETURNING id` do driver PG depende disso).
5. Atualize o seed (`init.js`) e esta doc.

## Inconsistências conhecidas (verificar antes de mexer)
- `transferencias.origem_id` é `NOT NULL`, mas `transferenciasController.criar` envia `origem_id || null` → falha se a origem não tiver id.
- `historico_movimentacoes.origem/destino` são texto livre (`"deposito: 3"`), sem FK; difícil de consultar.
- Sem FKs com `ON DELETE`; não há exclusão lógica além de `usuarios.ativo`.
- Sem constraint impedindo o mesmo equipamento em duas transferências ativas ou em dois eventos sobrepostos.
